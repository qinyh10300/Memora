# Memora Product Brief

Status: Approved baseline

Version: v0.1 planning baseline

Last updated: 2026-07-21

## One-line proposition

Memora 是一个面向个人与小团队的想法记忆库：用户快速记录带时间戳的想法，默认私有、按需共享，并通过有来源引用的 AI 助手找回、比较和总结个人或团队的想法。

## Problem

个人目前将想法分散记录在 GitHub、文档或其他零散位置，容易漏记，之后需要花大量时间翻找，也难以看出自己的观点如何随时间变化。

团队成员的想法分散在各自文档中。为了理解彼此的背景、进展和观点，成员需要逐篇阅读或反复开会，无法直接获得经过授权且可追溯的共享上下文。

## Target users

### Primary v0.1 user

愿意持续记录工作想法、需要回顾个人判断，并在一个四人小团队中选择性共享上下文的知识工作者。

### Future users

- 需要跨时间回顾决策和观点演进的个人用户。
- 需要异步共享进展、减少重复同步的小团队。
- 需要组织级权限、审计和私有模型部署的企业用户。

未来用户不构成 v0.1 的交付承诺。

## Jobs to be done

- 当一个想法出现时，我希望在很短时间内记录下来，以免之后遗忘。
- 当我记不清过去的观点时，我希望通过含时间和原文来源的回答快速找回。
- 当我怀疑自己以前有过类似想法时，我希望找到相似记录及其出现时间。
- 当我回顾一段时间时，我希望得到观点变化报告，并能检查报告依据。
- 当我需要了解同事或团队进展时，我希望只基于成员主动共享的记录获得总结。

## Product principles

1. **Capture before enrichment**：先保证记录可靠，AI 处理失败不能导致想法丢失。
2. **Private by default**：新记录默认只属于作者，分享必须是显式动作。
3. **Evidence over fluency**：回答是否有依据比语言是否流畅更重要。
4. **Temporal integrity**：历史不被静默改写，观点变化通过追加记录呈现。
5. **Unknown is valid**：证据不足时说不知道，不用推测填补空白。
6. **Simple core, replaceable AI**：产品核心不绑定单一模型或供应商。

## v0.1 scope

### Accounts and workspace

- 一个测试工作区。
- 四个预置账号，通过同一个公网网址访问。
- 不提供公开注册、邀请、找回密码或企业身份集成。

### Memory capture

- 用户创建一条纯文本想法。
- 系统自动记录作者和创建时间。
- 新记录默认私有；作者可以主动共享给整个测试工作区。
- 正文不原地修改。用户通过新建补充记录修正或延展历史，可关联原记录。
- 作者可以删除记录。删除后正文和 embedding 不再可检索。

### Browse and retrieval

- 用户浏览自己的记录以及其他成员共享给工作区的记录。
- 支持按作者、时间范围和可见性缩小范围。
- 支持关键词与语义相似检索。

### AI assistant

- 对当前用户有权访问的记录进行问答。
- 支持个人、指定同事和整个工作区范围，但不得越过共享边界。
- 支持时间范围和对话上下文。
- 事实性结论引用原始记录、作者和时间，并提供回到原记录的入口。
- 对“这个”“类似”“这段时间”等无法可靠解析的指代主动追问。
- 证据不足时明确说明信息缺失。

### Reports

- 按需生成个人或团队时间段报告。
- 个人变化报告应区分阶段、延续、变化、矛盾和证据缺口。
- 同事报告只能使用该同事主动共享的内容。
- 团队报告标明信息来自哪些成员和记录，不把 AI 推断表述为事实。
- v0.1 不提供定时生成或主动推送。

## Representative questions

1. 之前我对这个商业模式的看法是什么？
2. 我以前有没有出现过类似想法？分别是什么时候？
3. 总结我这段时间想法的变化，并生成一份带证据的报告。
4. 这个同事这段时间公开分享了什么经历、想法或进展？
5. 综合我们几个人这段时间共享的想法，生成一份团队报告。

这些问题将成为检索和回答质量评测集的起点。

## Non-goals for v0.1

- 文件、图片、音频、视频、网页或第三方知识库导入。
- 移动端原生应用和浏览器插件。
- 公开注册、复杂组织层级、细粒度群组分享和企业 SSO。
- 自动标签、知识图谱或完全自动化的主题体系。
- 定时周报、消息推送和会议系统集成。
- 用 AI 推断用户心理、绩效或未明确记录的经历。
- 微服务、Kubernetes、多区域高可用或大规模商业计费系统。
- 本地模型部署；v0.1 只保留可替换接口。

## Privacy and AI processing

- 用户记录可能被发送到配置的外部 AI 中转服务，用于 embedding、问答和报告生成。
- 产品测试前必须向四位用户明确披露该处理方式并获得同意。
- 发送给模型的内容必须先经过服务端权限过滤，只包含完成当前请求所需的最小记录集合。
- API Key 仅保存在服务器或开发者本机的未跟踪环境变量中，不进入客户端、不提交到 Git。
- 在引入企业用户前，需要重新评估供应商条款、数据保留、日志、跨境处理和本地模型方案。

## Validation experiment

四位测试者连续使用两周，每人至少记录十五条真实想法，并完成个人回顾、相似想法查找、同事进展总结和团队报告四类任务。

### Primary v0.1 signals

- **持续记录**：四位用户中至少三位达到十五条真实记录。
- **检索可信**：测试者认为至少 80% 的评测回答找到了正确或有用的记录。
- **引用完整**：所有事实性回答都附有当前用户可访问的来源；自动化越权测试为零泄漏。
- **总结有用**：至少三位用户认为个人或团队报告明显减少了手工翻阅时间。
- **记录摩擦低**：测试者能在约十五秒内完成一条纯文本记录。

“减少会议时间”是长期结果指标，不作为这次两周测试的主要成败判断，因为样本量和周期不足以可靠归因。

## Risks and assumptions

- 用户可能不愿额外打开一个 Web 产品记录想法，记录入口的摩擦是首要采用风险。
- 记录数量过少时，变化报告容易产生看似完整但证据不足的叙事。
- 语义相似不等于观点相同，结果必须允许用户检查原文。
- 外部中转服务的模型、接口稳定性和数据处理方式可能变化，必须隔离供应商依赖。
- 团队总结可能让用户误以为系统能访问私有记录，需要在 UI 和回答中持续展示范围。
- “可扩展到其他产品”暂时只通过清晰模块边界实现，不提前构建通用平台。

## Open product decisions

- 四个测试账号的名称、邮箱和初始密码交付方式。
- 删除记录的恢复期和服务器备份保留策略。
- 报告的默认时间范围和导出格式。
- 是否需要为每条补充记录显式选择被补充的历史记录。
- 两周测试结束后的反馈采集方式。
