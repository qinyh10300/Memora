# ADR-0003: Immutable memory revisions behind two edit actions

Status: Accepted

Date: 2026-07-26

## Context

个人 Markdown MVP 允许用户在记忆库中修改已经保存的内容。用户需要两种直观操作：

- 更新当前记忆，不在时间线中增加一项。
- 保存为新版本，让新旧内容都成为独立时间点。

现有产品约束禁止原地覆盖想法正文，同时要求删除时清除正文和向量。仅靠 `supersedes_id` 无法区分“同一时间线条目的内部修订”和“新的独立时间点”，也无法可靠决定删除范围。

## Decision

1. 每次正文变化都创建新的 `memories` 行，不原地修改正文。
2. 使用 `timeline_entry_id` 标识稳定的时间线条目。
3. 使用 `timeline_visible` 区分当前活动修订和仅供所有者查看的历史修订。
4. 使用 `revision_kind` 记录根记录、更新当前记忆或保存为新版本。
5. “更新当前记忆”沿用来源的 `timeline_entry_id`，隐藏来源修订并显示新修订。
6. “保存为新版本”创建新的 `timeline_entry_id`，来源和新版本都保持可见。
7. 活动列表、检索、报告和 AI 证据选择统一排除隐藏修订。
8. 修订历史只对条目所有者开放。
9. 删除时间线条目时，清除同一 `timeline_entry_id` 下所有修订的正文、向量和未完成任务。

## Why this option

- 用户看到的行为符合“覆盖”和“新版本”两种心智模型。
- 历史正文从不被覆盖，仍可恢复和审计。
- `timeline_entry_id` 给删除范围和历史查询提供明确边界。
- 复用现有 memory、embedding 和 outbox 结构，不引入第二套内容事实来源。

## Alternatives considered

### 原地更新正文并单独保存快照

会让 `memories.body` 变成可变事实来源，容易让引用、向量和快照产生不一致，因此不采用。

### 所有修改都创建新的时间线条目

实现简单，但不能满足用户明确提出的“更新当前记忆”，时间线也会被小修订淹没。

### 引入独立 memory revisions 表

模型更规范，但需要重构现有引用、向量、消息和删除路径。当前阶段使用同表不可变行即可保持边界清晰。

## Consequences

### Positive

- 所有修订都保留创建时间和独立处理状态。
- 活动召回只包含最新内容，不会把同一条目的旧修订重复提供给模型。
- 新版本仍能表达想法随时间的变化。

### Negative

- 更新当前记忆会产生额外 embedding 任务，并需使旧引用失效。
- 所有活动查询都必须复用统一过滤，遗漏会导致旧修订泄露。
- 生产环境若产生多修订数据，数据库迁移不能无备份直接降级。

## Revisit triggers

- 需要对修订进行协作评论、差异比较或恢复为当前版本。
- 单条记忆修订数量显著增长，需要独立冷热分层。
- 团队共享恢复后，需要定义共享记录修订的审批和可见性传播规则。
