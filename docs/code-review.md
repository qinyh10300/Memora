# Memora Code Review Guide

审查的目标是发现会影响用户、数据、权限和可恢复性的真实问题。先报告可操作发现，再给总体评价。

## Review order

1. **Authorization and privacy**
   - 是否在检索、Chatbot、报告、引用和直接 ID 访问中统一过滤权限？
   - 是否可能将私有正文、提示词、密钥或会话信息写入日志或客户端？
   - 是否存在只靠前端隐藏或提示词约束的权限规则？
2. **Data correctness and temporal integrity**
   - 是否会静默覆盖历史记录、丢失记录或让删除内容继续可检索？
   - 数据库写入、job/outbox 和 embedding 状态是否能从失败中恢复？
   - 迁移是否考虑现有数据、并发和恢复方式？
3. **AI grounding**
   - 事实性回答是否引用真实且仍有权访问的 memory？
   - 模型输出是否被当成权限判断或数据库事实？
   - 证据不足、供应商超时、限流和格式变化是否有明确降级？
4. **Behavior and API contracts**
   - 实现是否符合产品简报、活动计划和 ADR？
   - OpenAPI 与生成客户端是否同步？
   - 错误码、幂等性和边界输入是否稳定？
5. **Tests and operations**
   - 是否有跨用户反向权限测试和缺陷回归测试？
   - CI 是否不依赖真实生产密钥？
   - 日志、用量、健康检查和备份行为是否可观察？

## Finding format

每个发现包含：

- 严重程度与简短标题。
- 最小文件和行范围。
- 能触发问题的具体场景。
- 用户或系统影响。
- 建议修复方向；除非必要，不在审查中实现修复。

仅当问题会造成错误行为、越权、泄露、数据损坏、明显回归或维护者很可能接受修复时才作为发现。纯风格偏好、未证实的猜测和与变更无关的问题不应阻塞合并。

## Required review scenarios

- 用户 A 创建私有记录，用户 B 无法通过列表、搜索、Chatbot、报告和直接 URL 获得任何正文或片段。
- 用户 A 主动共享后，用户 B 可以查看和引用；取消分享后，后续检索立即不可见。
- embedding 失败或供应商不可用时，原始记录仍保存且可重试。
- 删除记录后，关键词、向量、引用和报告都不再返回正文。
- 报告中的事实结论都能追溯到来源；没有足够证据时明确显示缺口。
- API Key、密码哈希、Cookie 和私有正文不会出现在客户端 bundle 或普通日志中。
